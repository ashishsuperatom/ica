Project Portfolio — Semantic Model & Questions

As of July 2026  ·  Source live NetSuite (SuiteQL)  ·  Population 16,631 active projects

Three parts of one benchmark: the semantic model — the portfolio concepts we can compute on; the twelve questions those concepts answer; and the calculus — the pure form each question takes. Built from a real question list. Answers are marked honestly: ✓ answerable today, part a decode away, blocked where the data is not reachable — and each block names why (no history, or a permission the integration role lacks).

Time & effort Blocked · permission timebill · timesheet — denied

The billable / non-billable split. Time entries carry employee, hours, project and a billable flag — the whole basis of four of the twelve questions.

Blocked because timebill, timesheet and resourceallocation return HTTP 500 to this integration role, while job and transaction work — a permission gap, not missing data. Widening the role (Track Time + Employees) unlocks effort by person, non-billable %, utilisation.

People / employees Blocked · permission employee · resource — denied

The person and team dimension. Needed to roll effort up by person, team and practice.

Blocked because the employee / resource tables are permission-denied. Manager name is still reachable via the project's email field; full people analytics needs the role widened.

Portfolio history Not snapshotted no weekly capture

The missing "since last week". NetSuite holds today's RAG, not last week's — so movement can't be computed.

Would unlock RAG change vs last week · green→amber/red movement · RAG & budget trend · early warning. Begins the day we snapshot the portfolio weekly.

Go-live milestones Decode projectedenddate · project_end_date

When each project goes live. Date fields exist (projected end, project end date, gone-live flag) but are stored as text and need a clean date parse.

Would firm up "going live in N months", the go-live calendar, and slippage — once the go-live date field and its format are pinned with TO_DATE.

Invoicing & revenue Candidate transaction — reachable

Actual billed and revenue against each project — the other route to remaining budget and true margin.

Would unlock Budget vs billed · consumed-to-date · project margin · WIP. The transaction table (682k rows) is accessible — this is a modelling job, not an access gap.

Basis of preparation & the query— how this is computed
Show the query · developer
SELECT custentity_f5_prj_pillar AS pillar,
       custentity_f5_project_rag AS rag,       -- 1=Red 2=Amber 3=Green
       COUNT(*) AS n
FROM   job
WHERE  isinactive = 'F'
  AND  custentity_f5_project_rag IS NOT NULL
GROUP  BY custentity_f5_prj_pillar, custentity_f5_project_rag;
-- decode pillar/rag codes client-side; BUILTIN.DF() errors inside GROUP BY.

Population Active projects with a RAG set (1,710 active have none — excluded). Green ≈ 98.5% is genuine, not a filter artefact.

Active pillar Pillar = department; join custentity_f5_prj_pillar → department.id and filter isinactive='F' to drop retired pillars (only 2 stray projects). The same counts roll up the tree — group by department parent for a by-group (Enterprise Apps vs Microsoft) or by-division view.

Basis & the remaining-budget caveat— read before quoting "remaining"
Show the query · developer
SELECT custentity_f5_prj_pillar AS pillar, COUNT(*) AS projects,
       SUM(custentity_f5_total_project_budget) AS budget
FROM   job
WHERE  isinactive='F' AND custentity_f5_project_rag IS NOT NULL
GROUP  BY custentity_f5_prj_pillar;

Remaining = budget − consumed-to-date. Consumed needs time-cost (blocked) or billed-to-date (transaction — reachable). Currency mixed AUD/NZD; normalise before a single total.

Exhibit 3 Decode

Have the date fields — projectedenddate, custentity_f5_project_end_date, and a gone_live flag — plus the population filter.

Part III

Calculus — the pure form of a question

The calculus writes each portfolio question in the model's own vocabulary — nouns (project, pillar, RAG, budget, effort), a small set of operators, and its parameters (the go-live window, the attention set). It states what is asked and, by its types, whether the model can answer it. No implementation — the SuiteQL lives in the program, separately. Pure means free of implementation, not free of parameters.

Nouns — from the model
projectthe entity; grain of the whole portfolio · 16,631 active

pillarpractice line = a department; a 3-level tree (division → group → pillar), so the primary slice is also hierarchical · active = department not retired
budgeta measure, additive per project · remaining = budget − consumed
effort · billablehours from time entries · a flow · grain the model can't reach yet (permission)
person · teamthe people dimension · blocked (permission)

Operators — the algebra

assess(worst-of …)roll component RAGs into the overall RAG
Δ(m, vs: prior)change since last snapshot — needs history
top nrank — worst non-billable, biggest budget

What unlocks the rest the blocks are two moves, not ten

The twelve questions fail for exactly two reasons, and each has one fix. Six questions (4, 5 + trend) need a weekly snapshot — capture the portfolio's RAG and budget once a week and Δ becomes computable. Four questions (7-10) need one permission — Track-Time + Employees on the integration role, and effort/utilisation answers fall out of a single table. Plus one decode (go-live dates). So five answerable today become eleven with a snapshot job and a role change — no new modelling. That is the portfolio's path from reporting to a live, trend-aware, utilisation-aware view.
