### Decided, question 3 (2026-10-15)

- **Levels:** Superatom (our registry) and organisation. No project-level connectors: a project has connections, the instances. A person's unpublished connector is a draft kept in their UserDO (its bytes in R2 by hash).
- **Superatom's connectors** are available to every organisation by default; an organisation may restrict them (a separate case).
- **Publish** goes to the organisation as a proposal; the org admin approves; then any project admin adds connections with it.
- **A draft with a shared credential:** allowed to whoever may make shared connections in that project (project.connectors); anyone else uses a draft only with their own credential.
- **Builds:** GitHub Actions builds only the connectors whose folder hash is not in the registry; the same build tool runs locally, and whoever holds the registry key can publish by hand when Actions fails (as for the engine).
- **OS:** pure-JavaScript drivers preferred (one file for every OS); a native driver is declared in the manifest and built per platform, the engine taking its own. The datasource manager stays its own Node process under Electron.
- **Dependencies:** bundled at build time; nothing installed on the engine; what cannot be bundled is declared and checked before start. The framework (retry, pooling, record, SDK) is provided by the manager, not bundled.
- **Running:** the datasource manager supervises; ONE PROCESS PER CONNECTION (safety and robustness — the user's call; few engine connectors), restarted with backoff, a crash loop reported to Attention. The manager reconciles to the platform's list of connections; connectors never register themselves.
- **Credentials:** sealed on the platform, never on the engine's disk; shared ones in the connection's process memory; a person's fetched when a request runs for them (identity signed by the platform), held while in use, evicted idle, dropped on revoke. A person's credentials and their SSO flow: in their UserDO — to be planned carefully (question 6).
- **One door for every author:** a person on a laptop, a person in an engine environment and the connector agent all build with the same tool and register the same way.
- **To design (the user):** one lifecycle protocol for everything the engine runs — connectors, programs, agents: stored and emitted per project, acted on (restart, reload, new version) from the console and sacli, with permissions.

### Decided, question 6 — identity and access (2026-10-15; the user: "you make decision - based on simplicity and security … and enterprise requirements")

- **Identity is separate from transport.** Three modes, each connector's manifest naming those it supports and each connection picking one: a shared account (we enforce who reads what), a person's own key, a person's SSO/OAuth (the source enforces; ours apply on top). MCP's OAuth 2.1 is the third mode, a bearer key the first or second; new protocols land the same way.
- **A signed reader ticket on every data request**, from engine agents and the cloud sandbox alike: the platform signs it (Ed25519, its private key only on the platform) naming the person or agent key, the session, the connections allowed and an expiry (the turn, at most 15 minutes). The manager verifies it with the public key and resolves the policies itself from the platform (cached, cleared on change); nothing in a request names policies; no `raw` for agents. Missing or bad ticket: refused.
- **Agents run as a different OS user** from the datasource manager and the connection processes — without it an agent could read their memory or files, and the ticket would mean nothing.
- **Our policies apply on every connection**, per-person ones included: one model, always.
- **A person's credentials live in their UserDO**, sealed: keys they enter, and OAuth refresh tokens from "Connect my account" (authorization code + PKCE run by the platform). OAuth apps are registered once per organisation by the org admin (OrgDO). The engine gets a short-lived access token through ProjectDO → UserDO, never the refresh token; the UserDO renews once however many ask (the ChatGPT-login pattern). The person sees and revokes their accounts on their settings page; a revoke reaches the engine at once; a person leaving takes their credentials with them. No credential yet: the answer says to connect the account, with the button.
- **No person, no person's credential:** background agents (schedules, Systems 3 and 4) act as their agent key, on shared connections only.
- **Caches never cross people:** a result read with a person's credential is cached under that person; a shared-account result under the policies applied.
- **Every credential handed out is audited** (who, which connection, for which request) — never the credential.
- **APIs:** a row filter becomes an entity deny plus field masks on results; actions need their own permission (approval flow later).
- **Order:** the ticket, server-side policies and the separate OS user are built first, before the rest of the redesign — they close the holes live today.

### Decided, question 7 — connecting, pooling, timeouts, retry (2026-10-15, the user: "okay")

- The framework (the datasource manager, and the same SDK in the cloud sandbox) owns it; a connector supplies only open/close, its operations, and `classify(error)` → transient | auth | permission | bad request | unavailable.
- One pool per instance (manifest default, per-connection setting); a per-connection concurrency cap; a fair queue across people.
- Connect and query timeouts by default, a per-call override up to a cap; a query is cancelled when the turn that asked ends.
- Retry: reads only, transient only, 3 tries, jittered backoff, Retry-After honoured, one overall deadline. Auth: refresh the credential once, then "reconnect your account". Writes and actions never retried unless the connector declares idempotency keys.
- Circuit breaker per connection: open after consecutive failures (shown unavailable in its lifecycle record and Attention), probed again on a timer.
- Idle health: the connector's cheap test now and then.
- One record per call, engine and cloud alike: connection, who (from the ticket), operation, duration, rows, attempts, outcome.

### Decided, question 8 — indexing (2026-10-15, the user: "yes all good")

- The connector knows its system: `introspect()` (containers, fields, relations, optional cheap counts; paged with a cursor) and optionally `changedSince(time)`. The framework does the rest — scheduling, checkpoints, lease, resume, per-table fingerprints, storage (platform first, engine replica), search. The per-dialect indexers leave the platform for their connectors.
- One index for every connector: tables and columns, API entities and fields, and actions.
- Depth: structure always; statistics = row counts by default, deeper profiling sampled, opt-in per table, cost-limited (it runs on the client's database); AI descriptions and learned relationships later, each with its provenance, never overwriting the source.
- Refresh: on connect, daily by default (setting), on demand (console, sacli, agent), and at once for one table when a query finds it or a column missing. A schema change is a lifecycle event; concepts naming changed columns are flagged.
- Access applies to the index: denied tables hidden from that person's search, masked columns shown masked.
- Per-person connections: a per-person index (structure), built at first connect.
